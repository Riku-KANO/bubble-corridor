# 判断記録（ADR）

設計書「決めたこと」の表は作品の判断。ここは実装の判断を、新しいものを下に足す。

## ADR-0001 描画の土台は three/webgpu（WebGPURenderer＋TSL）（2026-10-21、仮）

- 設計書: 土台は Three.js と TypeScript。VR は WebGL2 の経路。M0 で WebGPURenderer の WebGL2 経路で VR が使えるかを確かめる。
- three r186 の WebGPURenderer は `XRManager` と `RenderPipeline` を持つ。材質と画面効果は TSL で書き、WebGPU・WebGL2（`forceWebGL`）・VR で同じ部品を使う。
- **M0 の関門1で確定する**。使えなければ VR 版だけ WebGLRenderer にし、共通部品のシェーダを2系統で持つ（設計書のリスク表）。

## ADR-0002 Blender のパイプラインを設計書どおりに使う（2026-10-21、改訂）

- 当初「Blender がない」としてコードのプレビズで代える判断をしたが、確認の誤りだった（PATH だけを見ていた）。Blender 5.2.2 LTS が `/Applications/Blender.app` にあり、ヘッドレス（`-b --factory-startup -P`）で glTF の書き出し、Cycles の焼き込み（Metal GPU）、Eevee の描画ができることを確かめた。
- 設計書「Blenderパイプライン」の流れに従う: レールと部屋の仮の形・カメラ・タイムラインマーカー・仮の楽曲でプレビズ（`blender/scenes/previz.blend`）を組み、通しの動画を Eevee で書き出す → 酔いの確認 → 部屋の本番の造形 → 見えない面の削除 → 焼き込み → 部屋ごとの glb とライトマップ、rail.json、cues.json を書き出す。
- 呼び出しは `scripts/blender.ts`（`BLENDER` の環境変数 → `/Applications/Blender.app/...` → PATH の順に探す）。造形はスクリプト（bpy）で作り、再現できるようにする。人が .blend を開いて直したら、書き出しのスクリプトで JSON と glb を作り直す。
- レールの最初の種は `generateRideData()`（TS）。プレビズに取り込んだ後は Blender が正で、書き出した `public/assets/rail.json` を実行時もテスト（`src/rooms/testing.ts`）も使う。
- 部屋の glb には画像を埋め込まない（ライトマップは別の画像。node のテストでも glb を読める）。部屋の担当は glb の形と焼き込みの上に、触れられる物・動き・ガラスの材質を TS で重ねる。
- 座標: rail.json と glb は three.js の向き（Y が上）。Blender（Z が上）との変換は書き出しと取り込みのスクリプトが受け持つ。
- `blender/scripts/common/` は案1と共有する（`src/core` と同じくコピーで揃える。ADR-0005）。

## ADR-0008 レールは1本、穏やかモードは標準の動きを上限以内に設計して満たす（2026-10-21）

- 設計書: 穏やかでは上下の動きと向きの回転を半分にし、乗車時間と楽曲との同期は変えない。
- 高さを半分にした2本目の道筋（gentleY）を持つと、部屋の形（水面すれすれの岸、膜、物との距離）を2本に合わせる必要があり、岸では「水面すれすれ」が両方で成り立たなかった（S-10 のレビュー）。
- そこで、**標準の動きそのものを穏やかの上限（上下 0.3 m/s、回転 7.5°/s）以内に設計**し、レールは1本にする。穏やかモードの違いは、万華鏡の模様の回転を止めること、VR の外周の暗さを強めることなど、演出の側で持つ。
- 時刻表の補間は単調な3次エルミート（createRide だけが補う）。s は3Dの弧長。Blender から 0.25〜0.5 秒刻みで書き出しても速度が階段にならない。

## ADR-0009 星の天球は「星の海の中の巨大なガラスの球」へ近づいてから入る（2026-10-21）

- レールの都合で、9:50 の中心から入口の膜までは約85m、出口の膜（夜明けの岸の頭）までは約62m で非対称（S-10 のレビュー）。
- 外殻を85m まで広げると岸の最初の約23秒が殻の内側になり、先読みの窓（膜の10秒後まで）と食い違う。
- そこで**外殻は中心から約60m 以内**に置き、天球の区間の前半（8:00〜約8:41）は、暗転の後に星が灯る星の海の中で、巨大なガラスの球を**外から見て近づく**導入にする。球を外から見てから中へ入る構図は、設計書の「部屋の入口で最初の一枚絵を設計する」に合う。後半は殻を何枚も抜けながら中心へ上昇し、出るときの最も外の殻が夜明けの岸への膜を兼ねる。
- 星（光を宿したガラス玉）は球の内側にも外側にも置く。

## ADR-0010 VR の描画経路の検証の結果と、three r186 の回避（2026-10-21、ADR-0001 の補足）

- WebGPURenderer の WebGL2 経路（forceWebGL）で immersive-vr が動くことを、IWER（Meta Quest 3 のエミュレーション）の e2e で確かめた（e2e/xr.spec.ts、5回繰り返して安定）。
- IWER だけで起きる three r186 の不具合を回避している: IWER の XRWebGLLayer.framebuffer が null を返し、WebGLState.drawBuffers の WeakMap の鍵になって毎フレーム例外になる。`renderer.xr.getBaseLayer().framebuffer === null` のときだけ、内部の WeakMap を null の鍵を許す形に差し替える（src/xr/system.ts の tolerateNullFramebuffer）。実機の投影レイヤーの経路には framebuffer がないので何もしない。
  - 外す条件: three か IWER が直り、e2e が回避なしで通ること。three を 0.187 以降に上げるときに確かめる。
- three r186 の setSession は投影レイヤーを作る前に foveation を当てるので、作った後に当て直す。
- **ADR-0001 は Quest 3 の実機で確かめるまで「仮」のまま**。実機で確かめる項目: 投影レイヤーの経路でエラー 0、天球（`?screen=home&t=588` から VR）で 72fps、MSAA 4/2/0・foveation 0/0.5/1・multiview の比較、座る/立つの高さと reset、指先とコントローラーで触れつまみでは反応しない、ヘッドセットを外すとポーズ、メニューの文字と外周の暗さ。

## ADR-0011 共通部品の和集合は案1の最新の main を基準にし、版はその次にする（2026-10-21、ADR-0005 の補足）

- 発案者の判断「和集合で統合」で、案1の src/core 0.3.0 を取り込んで 0.4.0 にする予定だった。実装の途中で、案1が並行で 0.4.0（S-08 GPU のフレーム時間、S-09 音の基礎）に進んでいたことが分かった（同じ版で中身が違うと、どちらの core:sync も止まる）。
- 決定: 取り込みの基準を案1の main の最新のコミット（b88d317、0.4.0）に取り直し、こちらは 0.5.0 にする。テストは基準のコミットの git の blob の SHA を埋め込んで照合する（案1がこの後に進んでも、こちらのテストは揺れない）。案1へは書き込まず、案1のセッションが次の core:sync で受け取る。案1がさらに進んでいたら、core:sync は「相手の方が新しい」で止まるので、そのときに次の和集合を作る。
- 案1の audio/（音の基礎）と案2の sound/（S-11）は役目が重なるが、ディレクトリが違うので並べて置き、整理は両方の作品の音が固まってから行う。
- 動きの曲線は案1の glassEase に一本化する（easing.ts の easeGlass は glassEase を呼ぶ）。ただし、カメラを正面へ戻す動き（src/input/look.ts）だけは easeInOutSine を使う。glassEase は最大の傾きが約 3.2 と大きく、VR と画面の見回しの上限（60°/s）を守ると戻しが約 3.2 秒まで伸びるため。画面の遷移の曲線ではなく、酔いの上限の中の動きなので、例外として残す。
- 名前のぶつかり: quality.ts は案1の QUALITY_PRESETS（段は low・mid・high）。案2の端末の自動判定と動的な解像度は quality-tier.ts（段は low・medium・high、型は TierPreset）。RoomContext.quality は TierPreset。


## ADR-0012 VR の暗転はゴンドラの縁を残し、画面の暗転は全体を黒にする（2026-10-21、S-24）

- 天球の頭の2秒の暗転（唯一の黒）は、画面では後処理（画面効果）で全体を黒にする。VR は後処理を使わないので、頭に付けた黒い球（半径 1.65m = ゴンドラの半径 + 目の高さ + 余裕 `XR.darknessMargin`）を `1 − 明るさ` の濃さで重ねる。
- 球は深さを見るが書かないので、球より手前で深さを書く不透明な物（ゴンドラの真鍮の縁・手すり・手先の目印）だけは暗くならない。VR では動かない基準を消さない（設計書 147 行「動かない基準があると VR での酔いが減る」）。透明の殻のガラスや星は暗くなる。
- 画面では見回す基準が画面の枠そのものなので、全体を黒にしてよい。
- 部屋の物が目から 1.65m 以内にあると、暗転の間も見える（いまの天球にはない。部屋の担当は RIDE-8 で 1.7m 以上離れる）。

## ADR-0013 部屋の境目と物との距離の確かめ方、扉の分岐の表し方（2026-10-21、S-21・S-22 のレビュー）

- **物との距離（RIDE-8）**: 軸に沿った箱で測る（`clearanceViolations`）。レールを囲む連続した形（壁・穹窿・鏡の板・六角の輪）は箱がレールを含んでしまうので `clearanceExempt` を付けてよいが、その物も三角形との最短距離で 1.7m 以上を確かめる（`shapeClearanceViolations`、区間の前後 3m まで）。除くのは通り抜ける物だけ（role が `membrane`・`shell`・`water`、または `userData.passThrough`）。exempt を付けるだけで RIDE-8 を外れる抜け道を作らない。
- **部屋の境目**: 膜は出る側の部屋が持つ（TRN-1）。出る側の部屋の形は区間の終わり（s1）から +1m まで、入る側の部屋の形は区間の始まり（s0）から +1m 以降に置く（重なって z ファイティングや二重の壁にならない）。距離の確かめは隣の区間まで測る。
- **扉の分岐（決定。発案者の判断 2026-10-21「案A」）**: 設計書は「手を伸ばした方、または長く見つめた方へゴンドラが進む」。レールは1本のまま（ADR-0008）、「選んだ扉が開き、その光と色で膜が満たされ、その中を進む。選ばなかった扉は閉じて暗くなる」で表す。選び直しは1拍に1回まで、万華鏡の色は扉が変わった時刻から 0.8 秒かけて混ぜる（光の明滅の上限。S-21）。道筋を扉の方へ寄せてくぐる案（案B）は採らない（レールのデータ・雨の部屋の形・動きの上限の検査を両方の道で持つ費用に見合わない）。
- **部屋の共有の擬似照明**: 部屋は `setGlassLighting` を呼ばず、`Atmosphere.glassLighting` に書く（`src/rooms/rules.test.ts`）。アプリがゴンドラのいる部屋の空気が変わったときだけ当てる。

## ADR-0014 撮影と部屋の先読みは three r186 の描画の内部の挙動に頼る（2026-10-21、S-30 のレビュー。ADR-0010 の補足）

撮影（src/photo/capture.ts）が画面の描画と同じシェーダを使い回し、見どころの最中に止まらないために、three r186 の次の挙動に頼っている。three を上げるときは e2e/photo.spec.ts（撮影の前後のフレームの間隔、撮影の時刻）と e2e/prewarm.spec.ts（部屋が見え始めるとき）で守る。

- **描画の文脈（RenderContexts）の鍵は、描画先の添付の形式と callDepth**。画面の描画は画面効果の scene pass の中（callDepth 1）、撮影は直接（callDepth 0）なので、同じ物でも別の文脈になり、シェーダを作り直す。撮影の下ごしらえ（compileAsync）は撮影と同じ描画先の条件で行う。
- **RenderObject は「物・材質・描画先・照明」で引かれる**。撮影の間だけ `renderer.lighting` を撮影専用の Lighting に差し替え、画面の描画の状態と分ける（VR の両眼と撮影の単眼が状態を壊し合わない）。差し替えは three 自身（PassNode）も使う手。例外のときも finally で戻す。
- **compileAsync は同期の部分で描画先と照明を取り込み**、ノードを組み立てる非同期の部分は元に戻した状態で走る。その中で `getOutputRenderTarget().multiview` を読むので、VR で multiview を有効にすると下ごしらえの鍵がずれる（いまは使っていない）。visible=false の物はコンパイルされない（撮影の部屋の下は、下ごしらえの同期の部分の間だけ visible を立て frustumCulled を外して準備し、必ず戻す）。物ごとの compileAsync(obj, camera, scene) はその物自身の visible だけを見る。
- **出力パス（トーンマップの変換の板）は描画先ごとに作り直され、1回目と2回目以降で別のコードになる**（uniform の宣言の順）。warmUpCapture を2回通す。
- **霧（scene.fog）は物ごとに霧のノードを作る**。部屋の空気が変わるたびに Fog を作り直すと、見えている材質がすべて作り直される。霧の物は使い回し、色と距離だけを書き換える（S-30 レビュー1巡目）。
- **compileAsync は window の rAF（yieldToMain）で主スレッドを返す**。immersive の間に window の rAF が止まる端末では作業が終わらず、撮影の列が詰まる。VR の間は `scheduler.yield` がない端末では下ごしらえをしない（src/app/app.ts の prepareShots）。
- **霧を null と行き来すると、見えている材質がすべて作り直される**（霧のある部屋とない部屋の境目、480 秒・750 秒で WebGL2 2 秒前後。S-29 の先読みで扱う）。
- **three の版は 0.186.1 ちょうどに固定する**（package.json）。上の挙動と、部屋の先読み（src/app/prewarm.ts）が使う次の点はこの版で確かめた。上げるときは e2e の photo・prewarm・xr を回し、写真と全部屋の絵を前の版と見比べる。
  - 部屋の先読みは、画面効果の scene pass の文脈（callDepth 1）で組むために、組む間だけ非公開の `renderer._renderContexts.get` を差し替える（無ければ差し替えずに進み、各段は try/catch と finally で元に戻すので、壊れても乗車は止まらず普通に描く）。
  - **透明で両面の材質は、そのままの compileAsync では組まない**。非同期の組み立てのときには side が両面に戻っていて、描くときと違う両面用のシェーダが作られる（ゴンドラの殻に白いヴェール。撮影の下ごしらえでも同じ。S-29）。材質を `Object.assign` で写して side を「裏面だけ」「表面だけ」に固定した写しで組み（compileDoublePassVariants）、three の組み立ての共有（材質の設定と side で引く）に頼って、描くときの裏面・表面の描き分けに使い回させる。そのあと小さな描画先に試しに描いて描画の状態まで作る。compileAsync(obj) は子までまとめて組むので、組む間だけ子を隠して物ごとに1回だけ組む。
  - 撮影の文脈と、画面効果なしの直接の描画の文脈は同じ鍵になる。
  - 環境画像は `scene.environmentNode` に PMREM のノードを1つ置き、部屋が変わるときは中身の画像だけ替える（ない部屋は強さ 0）。PMREM は描画の外で先に作る。
  - WebGL2（macOS の ANGLE/Metal）は、リンクが終わっても最初に描くときに GPU 側の状態を作って 0.5〜0.8 秒止まる。組んだ物を小さな描画先に1つずつ実際に描いて先に払う。
- 部屋の先読みの計画は、先の時刻（STREAMING.aheadSec + 10 秒）の計画で描く部屋も読み込みに足し（withLookahead）、読み込みが終わっても先読みが済むまでは場面に足さない（岸の頭で乗り場が先読みなしで足されて 0.29 秒止まった。S-29）。
- 時間に敏感な e2e（photo・prewarm）は、同じ端末で別の作業が GPU を使うと揺れるので、playwright の段を分け（main → photo → prewarm）、落ちたら1回だけ試し直す。単独で測った値（約 20ms）を基準にする。
